# SJP PvPワールド 開発ガイド

## 適用範囲

このファイルは、このMinecraftワールド全体と、その配下のデータパック・ワールドデータに適用する。

このプロジェクトは、Minecraft Java Edition 1.21.5向けの職業選択式チーム戦PvPゲームである。主な自作データパックは`datapacks/pvp`で、主要namespaceは`main`である。

このワールドでは、ゲームシステムのすべてがデータパック内にあるわけではない。コマンドブロック、手動作成したscoreboard objective、ワールド内entity、座標、建築物、region/NBTデータなどもゲーム実装の一部である。

## 最重要原則

- 分からない仕様を推測で補わない。
- データパック内に定義や呼び出しが見つからないだけで、未使用・不要・バグと判断しない。
- 外部入口、値の設定元、entity、tag、座標依存が疑われる場合は、可能な範囲でワールド側を読み取り調査する。
- ワールド側でも確認できない場合は、確認できたこと、分からないこと、必要な理由を整理してユーザーへ質問する。
- ゲームデザイン、職業設計、スキル仕様、数値バランスの最終判断はユーザーが行う。
- Codexは既存実装の調査、技術的選択肢の提示、実装、デバッグ、保守性・負荷の改善提案を担当する。
- 提案と実装を分ける。既存構造を大きく変更する改善は、ユーザーの承認前に実装しない。

## 対象バージョン

- Minecraft Java Edition 1.21.5を対象とする。
- `datapacks/pvp/pack.mcmeta`の`pack_format`は現在71である。
- mcfunction、item components、predicate、advancement、entity NBTなどは1.21.5で有効な構文を使用する。
- 古いMinecraftバージョン用のitem NBT構文が残っている可能性があるため、既存コードをそのまま正しいと仮定しない。

## 主要プロジェクト構造

- `datapacks/pvp`
  - 自作ゲームデータパック。
- `datapacks/pvp/data/main/function`
  - 主要function群。
- `datapacks/pvp/data/main/function/job_selection`
  - 職業選択時のtag、所持品、scoreboard初期値、attributeなどを設定する。
- `datapacks/pvp/data/main/function/pvp`
  - 戦闘中の共通処理と職業別の継続処理・スキル処理。
  - `pvp/pvp_control.mcfunction`は職業tagを確認して職業別functionを振り分ける中心的なdispatcherである。
- `datapacks/pvp/data/main/function/start`
  - 試合開始に関係する処理。
- `datapacks/pvp/data/main/function/stage`
  - ステージ選択、開始、終了判定、リセットなど。
- `datapacks/pvp/data/main/function/mode`
  - ゲームモード固有処理と共通リセット。
- `datapacks/pvp/data/main/function/waiting_place`
  - 待機場所・モード準備に関係する処理。
- `datapacks/pvp/data/main/function/training`
  - 訓練モード。
- `datapacks/pvp/data/main/function/first`、`gamerule`、`finish`、`rating`、`stats`、`time`
  - 初期処理、ルール、終了、レート、統計、時間処理など。
- `datapacks/pvp/data/main/advancements`
  - 古いスキル入口等の遺物が含まれる可能性が高い。現行機能だと決めつけない。
- `datapacks/pvp/data/main/predicates`
  - 条件判定に使用される。
- `Sjpジョブ情報.xlsx`
  - Googleスプレッドシートからエクスポートされた職業・アイテム・スキル・ショップ・用語の参照資料。

## function実装の慣習

- 職業選択処理は、原則として`job_selection/<job>.mcfunction`にまとまっている。
- 職業の継続処理は、原則として`pvp/<job>/<job>.mcfunction`を入口とし、個別スキルや段階処理を下位functionへ分割する。
- 共通エンジンを複数職で利用する場合、共通処理用tagと職業識別用tagを併用する。
  - 例：白魔法剣士は`Assist`と`WhiteSword`。
  - 例：暗黒騎士は`Wizard`と`WizardSword`。
  - 魔女、ポセイドンなどもWizard系の共通処理を利用する。
- スキルはscoreboardでMP、CT、CD、選択状態、入力時間などを管理し、tagや一時entityで発動中の状態を表すことが多い。
- スニーク、ジャンプ、歩行、ダッシュ、所持アイテム、custom nameなどが入力条件になる。
- 1つのスキルを、条件表示、発動判定、効果処理、終了処理の複数functionに分ける実装が多い。
- `@p`や実行座標に依存するfunctionが多い。呼び出し元の`execute as`、`execute at`、コマンドブロック位置を確認せずにselectorや実行コンテキストを変更しない。
- ファイル名、tag名、scoreboard名には歴史的な綴りや表記揺れがある。周辺の既存命名を尊重し、全体改名は別途承認を得る。
- コメントや表示名が古い職業名のまま残っている場合があるため、コメントだけを根拠に処理対象を判断しない。

## scoreboardの扱い

- scoreboard objectiveはユーザーがワールド側で手動作成している。
- データパック内に`scoreboard objectives add`がないobjectiveも正規の外部依存であり得る。
- 値の初期設定やゲーム状態の変更もコマンドブロックやワールド側から行われる場合がある。
- objectiveを削除、改名、統合する前に、次をすべて確認する。
  - データパック全体の参照。
  - コマンドブロック内の参照。
  - 現在の`scoreboard.dat`にあるobjectiveと値。
  - 表示用sidebar、belowName、list等への利用。
  - functionやtellraw、title、item book内のコマンドからの参照。
- 「設定元が見つからない」だけで初期値を追加しない。ワールド側設定との二重実行になる可能性がある。

## 職業・スキル・アイテム仕様資料

- 職業仕様は今後もGoogleスプレッドシートで管理する。
- ローカルの`Sjpジョブ情報.xlsx`は、そのエクスポート版として参照する。
- スプレッドシートとコードが食い違う場合、原則としてどちらかを自動的に正本と決めない。差異を報告し、ユーザーへ確認する。
- ユーザーが正しい側を確定した差異については、以下の「確認済み仕様」を優先する。
- 資料の空欄は「その要素が存在しない」とは限らず、資料未記入の可能性がある。
- 数値を比較する際は、基礎attribute、itemのattribute modifier、防具、effect、scoreboard補正を分けて確認する。最終値が同じでも実装箇所の違いによって装備解除時などの挙動が変わり得る。
- スキルのMP、CT、CDだけでなく、発動条件、対象範囲、持続時間、effect amplifier、回復量、ダメージ、召喚entityのNBTも照合する。

## 現行tag名に関する注意

- 現行コードでは雷神に`Thor`、殺人鬼に`Isaac`、羊飼いに`Shepherd`が使われている。
- スプレッドシートには`Thour`、`Isac`、`Shephered`という異なる綴りがある。
- 現行コード内のtagは複数functionとワールド側から参照される可能性があるため、資料の綴りだけを根拠に改名しない。
- tag変更が必要な場合は、データパック、コマンドブロック、現在存在するentity/player tag、選択看板等を一括調査して移行計画を提示する。

## ワールド側との連携

- コマンドブロックからfunctionが呼び出される。
- functionの継続実行や試合進行の入口が、データパックのtick tagではなくコマンドブロックにある場合がある。
- コマンドブロックチェーンの順番、条件付き設定、向き、座標は処理順序の一部である。
- regionファイルには建築だけでなくコマンドブロック実装が含まれる。
- entity regionデータには、職業選択、ゲーム進行、マーカー、召喚物等に必要なentityが含まれる可能性がある。
- `level.dat`、`data/scoreboard.dat`、`region`、`entities`等を単なるruntimeファイルとみなさない。
- NBTを調査する場合は、読み取り専用のツールや一時スクリプトを使用してよい。ユーザーの明示的な依頼なしにワールドNBTを書き換えない。
- 特定座標を変更する場合、function内だけでなく、コマンドブロック、armor standやmarker、建築物、リスポーン地点との対応を確認する。

## 欠落参照・遺物の扱い

- `main:job_selection/magicking`は魔王向けの実装予定入口である。
- 調査時に見つかったその他の欠落function参照は、コード更新過程で使われなくなった遺物である可能性が高い。
- 例として、Pirate2系、Wizardの古いMP charge、Pulpunteの古いsub、古いステージ入口などがある。
- ただし、遺物候補であっても、次を確認するまで削除しない。
  - 現在のコマンドブロックから呼ばれていないこと。
  - 書籍のclick event、看板、tellraw等から呼ばれていないこと。
  - 他functionから到達しないこと。
  - 将来実装用として残す意図がないこと。
- 古いadvancementも同様に、現行スキル入口ではない可能性が高いが、確認なしに削除しない。

## entity・item・リソースパック

- スキルはplayer以外に、armor stand、marker、mob、projectile、area_effect_cloud等を利用する場合がある。
- entity tag、team、owner、UUID、CustomName、座標、scoreboard値が処理の識別子になり得る。
- summonやkillの変更時は、生成側と回収・終了・リセット側を対で確認する。
- itemの`custom_name`、lore、custom data、enchantment、attribute modifiers、item idは発動条件として参照される場合がある。表示上だけの文字列だと判断して変更しない。
- このワールド専用リソースパックは存在するが、各プレイヤーが最新版を個別導入している。
- ワールド内の`resources.zip`は古く、現在は使用されていない。現行表示の検証資料として扱わない。
- 最新リソースパックがローカルに提供されていない場合、custom modelやtextureとの対応は確認不能として報告する。

## 変更時の優先順位

1. 現在のゲーム仕様・挙動を壊さない。
2. ワールド側との既存連携を壊さない。
3. 既存のコード構造、命名、scoreboard利用、function分割を尊重する。
4. 類似実装を探し、同じ種類の既存機能を参考にする。
5. 必要な範囲だけ変更する。
6. Minecraft Java Edition 1.21.5で正しく動作する方法を使用する。
7. 不明な仕様を勝手に決定しない。

一般的なベストプラクティスと異なることだけを理由に、既存実装を変更しない。Minecraft固有の制約や、ワールド側との連携理由が存在する可能性がある。

## 改善提案

次のような改善候補は積極的に報告する。

- tick当たりのコマンド数を大きく減らせる。
- selectorや全entity走査を限定できる。
- 重複functionを減らせる。
- scoreboard、storage、predicate、function macro等を使って保守しやすくできる。
- 新職業・新スキルを安全に追加しやすくできる。
- コマンドブロック依存を安全に減らせる。
- 一時entityやtagの取り残しを防げる。
- リセット漏れ、scoreboard初期化漏れ、attribute引き継ぎを防げる。

構造変更を伴う提案では、現在の構造、提案構造、メリット、デメリット、移行コスト、データパックへの影響、ワールド側への影響を説明し、承認を待つ。

## 調査・編集・検証の手順

1. 対象functionと同種の既存実装を読む。
2. 呼び出し元と呼び出し先を検索する。
3. 使用するscoreboard、tag、entity、item、座標を列挙する。
4. データパック外の入口や設定元が疑われる場合、関連するワールドNBTとコマンドブロックを読み取り確認する。
5. 仕様資料と比較し、差異が未確認ならユーザーへ質問する。
6. 最小限の変更を行う。
7. function参照、scoreboard名、tag名、item名の残存検索を行う。
8. 1.21.5構文と、変更した処理の開始・継続・終了・リセットを確認する。
9. ワールドを実際に起動する必要がある場合は、起動だけで多数のファイルが変わることを考慮し、ユーザーの許可とテスト範囲を確認する。

Minecraftを起動していない静的検証だけで、実機動作を確認済みと表現しない。

## Git運用

- 将来、`world`フォルダを直接Git管理する予定である。
- GitはCodexによるコード更新から過去バージョンへ戻れるようにすることが主目的である。
- commit・pushは、当面ユーザーへ対象変更を報告し、承認を得てから実行する。
- `git add -A`等でワールド全体を無条件にstageしない。
- 変更を次の3種類に分類する。
  - A：意図したゲーム実装上の変更。
  - B：Minecraftの起動・テスト・プレイにより偶発的に発生したruntime変更。
  - C：意図した変更かruntime変更か判断できないNBT・バイナリ変更。
- commit前に、commit対象、除外対象、判断保留対象をユーザーへ示す。
- テキストファイルは可能な限りdiffを確認する。
- NBT・region・entityファイルは、必要に応じて内容を比較する。
- Cに分類した変更を推測でcommit、削除、復元しない。
- `level.dat`、`scoreboard.dat`、region、entities等にはゲーム実装が含まれ得るため、安易に`.gitignore`へ追加しない。
- 明らかに毎回発生し、ゲーム実装と無関係だと確認できたruntimeファイルだけを`.gitignore`候補として提案する。
- destructiveなGit操作でユーザーのワールド変更を破棄しない。

## 今後AGENTS.mdを更新する条件

次の場合、このファイルの更新候補をユーザーへ提案する。

- 新しい職業共通基盤やステージ共通開始処理を採用した。
- scoreboard、tag、namespace、主要dispatcherを改名・再構成した。
- Googleスプレッドシートの正本運用や同期方法が決まった。
- Gitの初期化、`.gitignore`、commit対象の方針が確定した。
- 最新リソースパックがプロジェクト内で管理されるようになった。
- ワールド側コマンドブロックの主要入口が追加・移動・廃止された。
